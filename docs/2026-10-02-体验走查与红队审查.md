# DAOLOOK 真实用户走查、红队审查与修复

日期：2026-10-02。范围：本地 `http://127.0.0.1:8012`、普通账号注册、积分使用、项目设置、资料创作，以及 HTTP/任务/外部服务边界。

## 先复述计划，再攻击假设

你的计划是：让完全不懂营销原理和代码的用户，只需提供自己的业务资料、选想获得的结果，就能低成本拿到可信、容易发布、有机会带来相关流量、有效咨询或订单的内容。为此先从用户实际体验找出该省略、修正和隐藏的步骤；用浏览器走完注册、结算和设置，记录问题、直接修复、重新走查；同时对缓存、防爬、DDoS 和业务逻辑做对抗审查。完成后把代码提交并推送 main。

### 假设六个月后失败：最可能的三个原因

| 原因 | 被当成事实的假设与过度乐观处 | 触发条件 / 未考虑的失败情形 | 失败代价 | 最小证伪实验 / 本轮结果 |
| --- | --- | --- | --- | --- |
| 用户仍拿不到可以用的内容 | “业务资料 + 爆款写法”就足以自动生成可信且能成交的稿；把模型检查通过当成真实效果 | 资料缺失、价格冲突、旧优惠；模板把补资料和改稿工作退回用户；泛流量挤占有效客资 | 多次生成、改稿成本上升，流量看似增长却不成交 | 用同一真实业务的充分/稀疏/冲突资料各生成一轮，盲评事实错误、首次可发布时间和修改时间。**本轮只证明交付约束和演示标识可用，未验证真实模型质量、发布流量和成交提升** |
| 首页很简单，整条流程仍会中断 | 默认“用户知道账号、积分和项目在哪里”，把页面简洁当成流程简单 | 刷新、返回、切换项目、余额不足、邮件未配置；将管理员设置当作用户设置；不存在的支付入口让人找不到下一步 | 首次使用流失，资料重填，错误扣费或对服务失去信任 | 一个新账号从注册到提供资料、生成、查积分、修改设置，并刷新/切项目。本轮真实发现刷新丢草稿、项目不能修改、入口不明确并修复；注册和积分结算复测通过。当前没有在线支付能力 |
| 防护增加了阻碍，却挡不住成本攻击 | “限制 IP 请求数”就能防爬和 DDoS；认为取消等于撤回供应商请求、余额足以限制队列 | 零积分任务、多账号/多 IP、慢连接、重复提交、DNS 指向私网、上游超大响应；企业 NAT 用户共享 IP | 服务不可用、供应商账单增长、资料泄漏；正常用户被误伤 | 在临时 DB 和本地短时连接上测试重复提交、容量上限、取消、私网解析、缓存隔离与限流。已加入回归测试；未进行公网攻击或压测。带宽清洗和分布式限流未部署 |

**结论：先做上述最小实验，验证后再扩大投入。** 本轮已完成体验与资源边界实验，并直接修复可复现问题；不需要推倒重来。真实业务效果仍需下一步小规模发布实验，不能用演示数据宣布成功。

更简单的实现路径：主入口只保留“用我的资料创作”，参考内容改写作为可选入口。只要求用户选结果、给资料、拿稿；搜索、提示词、事实引用、去重、模型路由和重试由系统承担。不要先增加更多自动化平台接入或要求用户学会一套营销方法。

## “更好的输出”如何验收

对用户：**少填、少等、少改，拿到能让合适的人看懂价值、愿意咨询或购买的内容。**

内部验收分两层，不能混成一个“爆款分”：

1. 交付质量：事实有依据、无空占位、表达具体、对应目标人群、下一步行动明确；衡量第一条可用稿的时间、修改时长、实际发布率和每条可用稿总成本。
2. 业务结果：曝光目标看相关触达；咨询目标看有效咨询及咨询成本；成交目标看订单、毛利和退款。比较同账号、同平台、相近主题和相同观察期，区分自然与付费流量。

当前引用校验只证明引用原文存在，不能证明整篇语义真实或预测爆款。客户只看到必要的缺项提示，不需要看到这些验收公式。详见 [内容效果升级](内容效果升级.md)。

## 真实浏览器走查方法与边界

- 使用 Codex 浏览器控制，真实输入、选择、提交、返回、刷新、切项目，保存截图及页面文本。点击工具存在无响应情况后使用真实键盘 Enter/Space 激活控件；未使用脚本修改页面状态或直接调用 API 来冒充 UI 成功。

## 按严重度排序的问题与修复

P1：可能造成业务资料丢失、费用/资源滥用或安全边界被突破。P2：阻断或显著增加使用成本。P3：说明与入口不清。证据类型明确区分浏览器、隔离对抗测试和代码复核。

| ID / 严重度 | 复现步骤 | 根本原因判断 | 修复方案及验证 |
| --- | --- | --- | --- |
| UX01 / P1 | 首页填主题、目标、业务资料→浏览器刷新；输入归零 | 输入只在内存S中，没有草稿恢复 | 当前标签页按用户+项目保存白名单字段，24h过期、退出清除；不保存密码/图片base64。浏览器23、40–41及前端隔离/过期测试通过 |
| SEC01 / P1 | 本地慢连接占住请求且不结束；并发连接继续增长 | ThreadingHTTPServer没有连接容量与绝对接收截止 | 64连接、15秒接收截止、请求头/正文上限、超量503；缩小参数的慢连接测试证明拒绝及释放后恢复 |
| SEC02 / P1 | 并发请求与大量新身份访问；反复申请演示账号 | 原限流表无锁/无容量，部分认证入口无防护 | 有界线程安全token bucket，IP/账号/邮箱/昂贵操作分层限流、429及Retry-After；伪造代理头不能默认取得新身份 |

## 缓存、防爬与 DDoS 的交付边界

已实现应用层请求资源上限、分层限流、重复任务防护、安全外连、静态缓存、私有响应不缓存、可信代理配置。没有使用一刀切User-Agent黑名单或给每个用户增加验证码。合法账号保存自己可见的内容无法由这套限流彻底阻止。

已提供 [Nginx示例](../deploy/nginx.conf.example) 和 [部署说明](../deploy/HTTP防护与部署.md)，**未部署到公网**；本机没有nginx，未执行nginx -t。应用内限流是单进程的，不能防止带宽耗尽、分布式IP洪泛、源站绕过或多账号积累的磁盘增长。线上需要真实域名/证书、可信代理、CDN/WAF与防火墙，另行做部署验证。

实现依据：[MDN缓存语义](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching)、[Nginx请求限流模块](https://nginx.org/en/docs/http/ngx_http_limit_req_module.html)。[Python官方文档](https://docs.python.org/3/library/http.server.html)明确内置HTTP服务不建议直接用于生产；本轮加固不等于把它替换成生产服务器。
