## 与旧版的关键差异

1. 平台分化:4 条 Prompt 按平台与任务(拆解/创作)分别改写,不再共用一段。
2. 贴合 Schema:分析维度名与 `schemas/*.schema.json` 的 10 个 prefixItems 一一对应;创作字段逐个给出硬性要求(字数、结构、数量)。
3. 防编造强化:拆解侧「归因到结构、数据克制、画面推断需注明」;创作侧「缺失事实必须进 missing 字段、正文占位」,与系统已有的 JSON Schema 校验和「素材不可信」系统指令叠加。
4. 明确边界:测试与发布仍走 Draft → Test → Published 版本链;发布自动归档旧 Published,可回滚。

## 生效条件

拆解/创作真实调用需要先在管理后台配置模型服务(Base URL / Key / 模型 ID);演示模式的预置样本不经过模型,不受 Prompt 影响。「结构测试」在未配置模型时会报「请管理员配置并启用对应任务的模型」。

## 待写入创作 Skill：内容方向，而不只是仿写

口播《郑州帮不会死，只会进化》已补进产品 PRD 第 9.1–9.3 节。以下要求已写成创作 Skill v5（`server/skills.py`，启动时自动发布），同时落进 JSON Schema、`validate_creation` 结构校验、稿件卡片与导出：

1. 小红书每条稿先标明方向，只有视频里的两种：测评（权威、建信任、帮人做决定）、钓鱼帖（提问或场景开场，截流，把泛流量引到产品能回答的点）。
2. 一次返回 6 到 8 条。资料够用时，同一批必须同时出现这两种方向；只够一种时，每条用不同切角，并在 `missing` 写明另一种缺的事实。
3. 生产标准写成「好生产、好复制」。语气服从项目资料，调性和人设不能代替方向。
4. 小红书输出增加评论布局：气氛、知识、置顶，对应发布后一小时的第一波。店铺名和经历只来自资料。不写多账号对敲、不写伪装路人、不编造回购。
5. 抖音先标明这条是建立信任还是截流，再写口播。不另造视频里没有的抖音类型。
6. 矩阵账号和投放不进 V1 执行。稿件说明保留：自然流点击率稳定在 20% 以上再考虑小额投放，投放只放大已验证的结果。

## 版本收敛(应用户要求)

v3 经确认后直接置为生效版,v1/v2 已删除;每类 Skill 只保留一条「生效中」记录。此后发布新版本时,服务端仍会把旧生效版转为「已归档」(可在界面回滚或手动清理)。

## v5 相对 v4 的修正

- 删除固定的「闺蜜分享」口吻，改为语气服从项目资料；删除「我挖到宝了」这类会诱导虚构经历的示例。
- 每条先填 `direction` / `role` / `angle`，再写表达；方向只允许两种。
- 资料只够一个方向时允许整批同方向，但必须在 `missing` 写明另一方向缺哪项事实（校验会检查）。
- 小红书新增必填 `comment_layout`（气氛、知识、置顶、发布后一小时）。
- 加入「好生产、好复制」生产标准与投放原则（自然流点击率稳定 20% 以上再考虑小额保护性投放）。

## 2026-09-26 发布：拆解 v4 + 创作 v5

- 发布方式改为启动时一次性写入并生效（设置项 `skill_release_2026_09_26` 记录已执行），旧生效版本归档可回滚。
- 修复：此前创作时模型只收到参考的公开数据，没有收到拆解结果；现在同时传入 `analysis`（十维拆解）和 `previous_outputs`（同一参考已生成稿件的方向、切角、标题），并去掉原始接口节点，减少无关上下文。
- 拆解 v4：说明各输入字段含义（基线、发布时间、口播文字来源），有口播时以原文为依据，没有时写明推断来源；爆点判断增加「更适合迁移成哪种内容方向」，为创作选方向提供依据；小红书互动设计按气氛/知识/置顶概括评论区。
- 创作 v5：每条稿只挑一条可迁移机制；给出拉开切角的四个维度（人群、场景、决策阶段、问题类型）；再次生成不得重复已有「方向+切角」。
