# Daolook 升级建议与 GitHub 选型

2026-11-26 · 基于本地版本 `8a04694`

Daolook 服务于有具体业务目标的创作者。用户给出资料或参考，希望拿到一篇事实准确、符合平台习惯、自己能发或能拍的内容，发布后再用曝光、咨询或订单判断这次选题值不值得继续做。现有产品已实现多稿生成、首选稿、编辑与版本恢复、发布确认及分期效果记录。下一轮最值得投资的是稿件可信度、从参考到动手的距离，以及每篇真正用得上的稿件要花多少时间和成本。[产品流程](../README.md) · [效果统计口径](内容效果升级.md)

## 优先顺序

| 顺序 | 交付 | 投入判断 | 验收依据 |
| --- | --- | --- | --- |
| 1 | 国内稿件的价格、条件和购买入口可逐句核对，定向重写保留业务上下文 | 小到中，可先修重写 | 冲突示例被准确标出，正常示例可通过，重写回归覆盖两个平台和三个目标 |
| 2 | 在「今日推荐」「往期推荐」看完即可带入创作 | 小，复用现有草稿和参考流程 | 两次操作内到达已带参考的草稿，今日、特刊、已移出候选池的往期均可用 |
| 3 | 建立真实业务样本盲评，决定提示词、模型和生成策略何时值得升级 | 中，主要投入是编辑标注；和前两项同步开始 | 同一份简报对照旧版，报告可发布率、首稿确认覆盖率、编辑分钟数和模型成本 |
| 4 | 提高每天能入选的新拍法，同时校准国内前三条参考 | 中，需要编辑看样片和真实候选列表 | 海外看连续日期的重复与可拍率，国内看留出搜索结果的前三条可用率 |
| 5 | 从一个账号、一种导出表开始批量回填发布效果 | 小到中，取决于能否拿到稳定样表 | 减少回填时间，同一份表重复导入两次数据一致，7 天指标覆盖率提高 |

投入为按当前代码复用程度判断的相对工作量。以下样本量和阈值是试点建议。

## 1. 让每次改稿都守住业务事实

在内存合成样例中，资料写「售价199元，仅限到店」，稿件正确引用了「售价199元」，正文却写「现在只要99元」。交付检查仍返回 `checked`。现有检查能确定引文存在，但没有把这句话的价格与对应商品、渠道及条件核对。另一个可复现问题出现在定向重写。按系统提供的返回格式模拟一次成功响应，旧稿中的业务目标、配图 ID 和质量状态全部丢失；任务随后会将这份响应写回整稿。这也可能使稿件退出按目标筛选的效果反馈。[引用检查](../server/content_quality.py) · [重写适配器](../server/adapters.py) · [写回与历史反馈](../server/jobs.py)

**最小改动。** 重写由服务端将允许改动的文案字段合并回当前版本，保留目标、选用素材与来源，重新计算变更内容的质量状态。首批核对价格、规格、有效期和购买入口，把具体主张连到所选资料的原文片段。遇到多规格、限定渠道、过期临时资料或来源冲突，编辑器在相关句子旁展示待核对项。拿「199 元到店价、99 元仅限会员」等正常组合做对照，避免凡是两处价格就报警。沿用原有版本锁、失败退款和人工确认入口。[手动编辑的字段合并与复核](../server/editing.py)

**GitHub 取舍。** LangExtract 能把结构化抽取结果定位到原文字符区间，适合借鉴其来源定位方式。首版复用 Daolook 已有资料 ID、快照和引用即可；遇到不同商品的多重条件，仍需单独判断主张与证据是否相符。[google/langextract · Apache-2.0](https://github.com/google/langextract)

## 2. 把每日原片接回当前项目

「易拍片库」已有“用这个创意创作”，默认的「今日推荐」、往期卡片和播放器却只支持看片或站外观看。后端可以从当期推荐走到真实模型并生成三个方案，项目在 11 月 21 日已记录过一次这样的独立验收。现在缺的是用户点得到的同一条路径。[每日卡片和播放器](../web/overseas.js) · [真实模型验收记录](examples/open-desk-from-daily.md)

**最小改动。** 在日刊播放器内放一个主操作「用这条拍法创作」，无法内嵌播放的作品在卡片上提供同一动作。打开草稿时带上原片和已有创意说明，提交生成时才沿用现有计费。服务端按期号和原片标识核对归档快照，避免同日自动版与人工特刊的位置串片，也覆盖已移出候选池的历史作品。仅存原链接的旧记录只带链接。验收时从实际界面走完整链路，检查提交任务引用的作品与用户看到的一致。[现有参考解析](../server/overseas_library.py) · [归档快照与特刊](../server/overseas_editions.py)

## 3. 用真实简报决定升级是否值得

仓库已有 40 组合成结构样例，也记录过海外真实模型生成和分镜对照。本次对本机工作库只做聚合统计，36 篇未删除稿件中，按工作台正式稿口径计为 0 篇。海外验收任务存放在独立库，样例文档也说明尚待实拍。因此当前材料可验证流程和具体缺陷，尚不足以估算真实用户的采用率、改稿成本或成交提升。[测试说明](../README.md) · [海外试拍简报](examples/open-desk-saturday.md)

**第一轮。** 邀请试点商家提供 30–50 份脱敏业务简报，国内覆盖小红书与抖音的曝光、咨询、下单目标。包含无购买入口、价格冲突和资料不足的案例。按商家留出一组，调提示词时看不到这组。用相同输入生成现版和候选版，随机打乱顺序，让编辑选哪篇愿意发、改了几分钟、发现哪些事实错误。海外另挑少量简报，请运营用约定的人数、场地和道具实拍，记录哪一个镜头需要返工。

**工具与成本。** Promptfoo 适合批量运行相同样本、比较版本并执行自定义断言。接到现有 Python 生成入口，日常 CI 回放固定响应，发布前再用有预算的真实模型跑留出集。当前项目 CI 用 Node 20，Promptfoo 最新安装文档要求 npm/npx 使用 Node 22.22.0 及以上，建议使用独立评测任务并固定版本。另记录整批重试的次数和 token，若重试占比高，可试验只重写失败稿，整批再次检查条数与角度重复。[现有 CI](../.github/workflows/ci.yml) · [当前模型重试](../server/adapters.py) · [promptfoo/promptfoo · 核心 MIT](https://github.com/promptfoo/promptfoo) · [官方运行环境](https://www.promptfoo.dev/docs/installation/)

**管理指标。** 同时报告「提交满 7 天的正式创作批次中，至少发布一篇的比例」和「同批次中至少确认一篇的比例」。分母以提交时的批次为准，保留未确认、未发布和后来删稿的批次。沿用首篇确认耗时中位数，另记实际编辑分钟，区分等待和返工。以试点全部生成、重试和改稿的可归属供应商费用除以人工确认的不同稿件数，得到每篇可发布稿成本；缺失用量列覆盖率，估算按模型费率注明。积分、预算预留和供应商实付分别记录。[现有确认统计](../server/workspace.py) · [调用用量与预算](../server/spending.py)

## 4. 让用户看到的头几条参考更值得用

**海外选片。** 只读核对本机片单日期 11 月 23–26 日的四期自动首屏，每期 10 条，40 个位置合计只有 12 个不同原片链接，三个相邻日都重复 8 条。该库最近一次同步新增 15 条候选，首次达到现有规则的为 0。选择器已经优先避开昨日作品，也考虑拍法和发布者。下一步先抽审未入选候选，记录是画面平常、动作难复拍，还是说明文字遗漏了精彩段落。[现有选片逻辑](../server/overseas_daily.py) · [原帖说明匹配规则](../server/overseas_visuals.py)

给编辑一周固定审片时间。对可处理的授权短片，可选用 PySceneDetect 找切镜位置、取代表帧；一镜到底的动作另取开头、中段、结尾帧。由编辑标注“哪一秒出现什么变化、用什么道具能复拍”，供后续创作和抖音拆解引用。没有画面依据时保留原帖说明的来源标记。连续两周记录每天首次入选数、相邻首屏重复率和编辑盲审可拍率，先试能否把当前观察到的 80% 重复降到 50% 以内，同时守住可拍率；库存短缺时明确展示往期精选。[Breakthrough/PySceneDetect · BSD-3-Clause](https://github.com/Breakthrough/PySceneDetect)

**国内参考排序。** 用默认权重做了一个合成对照。仅知道「一天前发布」，得 96.7 分；同样一天前发布，外加 1,000 赞、100 藏、100 评、1,000 粉、赛道互动中位数 600，得 50.1 分。原因是得分会按已有维度重新分配权重。校准脚本又在同一批数据上寻优和报告 AUC，容易高估新权重的效果。[评分实现](../server/ranking.py) · [校准脚本](../scripts/calibrate_ranking.py)

先将互动证据不足的内容单列为待核实候选，再取真实关键词与博主列表，分别标记“相对表现异常”和“本项目值得借用”。用不同账号、搜索词或较晚日期的整批候选做留出，对比来源原序、点赞序和现有排序。主指标看前三条中编辑愿意借用几条，辅看 NDCG@3（好参考是否排得靠前）及数据覆盖率。ranx 放在离线评估环境即可。[AmenRa/ranx · MIT](https://github.com/AmenRa/ranx)

## 5. 让发布反馈以更少手工回到创作

工作台已有截至目前、24 小时、7 天、30 天四种口径，历史反馈取同项目、目标和相应平台近期更新的最多 12 条。现有汇总和反馈选择尚未按发布账号切分。建议选一个愿意提供后台导出样表的账号，跑通「标记发布 → 绑定平台作品 ID → 导入效果 → 下次创作看同账号反馈」。[分期快照](../server/production.py) · [反馈选择](../server/jobs.py)

首版用现有 Python CSV 与 SQLite，匹配键包含项目、平台、账号与作品 ID，写入时绑定稿件版本和观察期。导入前列出无法匹配或有冲突的行；同一观察期重导更新原值，空值和零分别保留。样表只有累计数据就写“截至目前”，咨询和订单可沿用人工补录。学习时分开自然与付费样本，显示可比稿数。用同一运营者一周的回填分钟数，以及「发布已满 7 天且填了 7 天目标指标的正式稿 ÷ 已满 7 天的正式发布稿」验收。多平台模板出现后，可用 Frictionless 在开发阶段检查字段类型和错误行。[frictionlessdata/frictionless-py · MIT](https://github.com/frictionlessdata/frictionless-py)

## 下一项产品投资

若盲评显示稿件已可用，但运营时间主要耗在小红书配图，可做「一篇稿的图文发布包」。从一篇已确认稿和项目实拍图生成封面、两张关键信息内页及可复制正文，统一预览、一次导出。PRD 点名的 agent-xiaohongshu-workbench 已展示 1–6 张配图与全文预览，值得借鉴交互。Daolook 可复用自己的排版和版本历史，通过同一编辑完成一篇图文的总时间决定是否扩展。抖音同类项目 douyin-ingest 的逐字稿校正格式也可参考；当前已有 TikHub 与口播转写，新增采集器的投入排在真实返回样本验证之后。[现有封面能力](../README.md) · [agent-xiaohongshu-workbench · 源码 MIT](https://github.com/EthanYoQ/agent-xiaohongshu-workbench) · [ltppp/douyin-ingest · Apache-2.0](https://github.com/ltppp/douyin-ingest)
